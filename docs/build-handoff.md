## 0. How to use this handoff

Three documents form the contract:

| Document | What it is | When you read it |
|---|---|---|
| `build-handoff.md` (this) | Stack, repo layout, milestone plan, conventions | Before writing any code |
| `contracts.md` | Schemas, tool signatures, validation rule catalogue, storage interface, DDL | Before each milestone that touches them |
| `worked-example.md` | The location-onboarding blueprint and dataset, plus the broken-variant corpus | At M0, committed as test fixtures |

Build one milestone per session. Each milestone below states its acceptance criteria. Do not start a milestone until the previous one's criteria pass. If a milestone's spec is ambiguous, prefer the interpretation that upholds the ground rules in section 1, and record the choice in `DECISIONS.md`.

**Do not redesign.** The PRD went through four rounds of decisions with the product owner. If something looks wrong, note it in `DECISIONS.md` under "Questions for the owner" and build what is specified. The exception is a genuine contradiction between documents, which you should surface rather than resolve silently.

## 1. Ground rules

These are invariants. A change that violates one is a bug, no matter how convenient.

1. **The runtime is read-only.** No code path lets a running agent write to a dataset. `record_step` writes to a run. Nothing writes to a dataset except the authoring flow.
2. **The service never grades.** It stores expectations and emits evidence. There is no comparison logic in the server. The three comparison helpers live in the Python client as pure functions.
3. **The service never gates.** No tool returns a non-zero exit code, raises on a policy violation, or refuses to serve because something looked wrong. Mismatches produce warnings attached to the response and to the stored run.
4. **No LLM inside the service.** No model client, no API key handling, no judge. The service hands out skeletons and validates what comes back.
5. **Datasets are immutable and versioned.** Edits are copy-on-write. A run pins a version at start and reads that version for its whole life.
6. **No hard delete.** Archive only.
7. **Validation is strict at write time and absent at read time.** A dataset that got into the store is trusted by the read path.
8. **No dataset without provenance.** Title, intent, complete labels and a named author are required at submit. There is no partial-provenance path, no "fill it in later", and no default author.
9. **Determinism.** Same seed plus same blueprint version yields the same expansion. All randomness flows through a single seeded source. No `random()`, no `uuid4()`, no `datetime.now()` inside generation or expansion code paths.

Rule 9 deserves a note: run ids are generated by the *client*, not the service, so `uuid4()` is correct there. It is generation and expansion inside the service that must be seeded.

## 2. Stack

Locked. Rationale given so you understand the constraint, not so you can relitigate it.

### Service (Python)

| Concern | Choice | Notes |
|---|---|---|
| Language | Python 3.12+ | The eval side is Python. |
| Packaging | `uv` with `pyproject.toml` | Fast, lockfile-based. |
| MCP server | Official SDK, `pip install mcp` (v2.x) | v2 renamed `FastMCP` to `MCPServer`: `from mcp import MCPServer`, tools via `@mcp.tool()` with input schemas derived from type hints. | Models | Pydantic v2 | Envelope models, request and response types. |
| User schema validation | `jsonschema` (Draft 2020-12) | Blueprint node schemas are user-supplied JSON Schema. Validate fixtures against them with a real JSON Schema engine, not Pydantic. |

| Document storage | `pymongo` | Mongo adapter. |
| Tests | `pytest`, `pytest-asyncio` | In-memory MCP client for tool tests. |
| Lint and types | `ruff`, `mypy --strict` | Strict from M0. Retrofitting types is worse. |
| Observability out | `opentelemetry-sdk` plus OTLP exporter | M10. |

## 4. Milestones

Each is one session. Acceptance criteria are the gate.

### M0: scaffold

Repo, `pyproject.toml` with all dependencies pinned, `ruff` and `mypy --strict` configured and passing on an empty tree, `pytest` running, GitHub Actions CI running lint plus types plus tests, `CLAUDE.md` written from section 5, `DECISIONS.md` created, and all fixtures from `worked-example.md` committed under `tests/fixtures/`.

**Accept when:** `uv run ruff check`, `uv run mypy src`, `uv run pytest` all pass in CI on an empty test suite, and the fixture files are present and parse as JSON.

### M1: domain models

Pydantic v2 models for Blueprint, Node, Edge, EntitySchema, LabelSchema, Dataset, Entity, NodeFixture, ExpectedOutcome, Run, StepRecord, Warning, and the error envelope. Exact shapes in `contracts.md`. Emit the Blueprint and Dataset JSON Schemas from the models into `schemas/` at build time, since the web app needs them for live validation.

**Accept when:** every fixture in `tests/fixtures/blueprints/` and `tests/fixtures/datasets/` round-trips through the models without loss, and the emitted JSON Schemas validate those same fixtures under a Draft 2020-12 validator.

### M2: the validator

**This is the heart of the product. Build it standalone and test it hardest.**

Implement every rule in the validation catalogue in `contracts.md`. Each rule has an id (`BP-001`, `DS-014`, and so on). `validation/registry.py` maps rule id to callable so the catalogue is machine-checkable rather than prose. Validation returns a list of structured errors, each carrying rule id, JSON pointer to the offending location, human message, and the section of the skeleton it belongs to. It never raises for a validation failure.

**Accept when:** every file in `tests/fixtures/broken/` is rejected with exactly the rule ids its manifest declares, no more and no fewer; the valid fixtures pass clean; and a test asserts that every rule id in the catalogue has both an implementation in the registry and at least one broken fixture exercising it. That last assertion is what stops the catalogue drifting from the code.

### M3: storage, SQLite first

The adapter Protocol from `contracts.md`, plus the SQLAlchemy implementation against SQLite. Alembic migrations. Blueprint persistence with immutable published versions. Dataset persistence with monotonic versioning, copy-on-write on edit, and the archive flag.

**Accept when:** an integration test writes a blueprint, publishes it, fails to mutate it, writes a dataset, edits it, reads back both versions distinctly, archives it, confirms it is hidden from find and still readable by id and version, and confirms no code path deletes a row.

### M4: MCP server, blueprint and dataset reads

`MCPServer` with stdio and streamable HTTP transports. Tools: `blueprint_upsert`, `blueprint_get`, `blueprint_list`, `blueprint_validate`, `blueprint_diff`, `dataset_find`, `dataset_get`, `dataset_archive`, `dataset_restore`, plus `store_status`, `label_vocabulary`, `agent_list`.

**Accept when:** an in-memory `Client` connected straight to the server object exercises every tool, `blueprint_diff` returns a structured diff and never a failure signal, and label queries return deterministic ordering for identical inputs.

### M5: the skeleton pipeline

`dataset_skeleton` returning a skeleton plus `skeleton_id` plus the ordered section manifest, **provenance first**. `dataset_fill_part` accepting one section, validating it locally at schema level, and rejecting a node section referencing an entity not yet declared. `dataset_submit` running full cross-cutting validation then storing. Server-side partial state keyed by `skeleton_id`.

**Accept when:** the worked-example dataset can be filled in five separate `dataset_fill_part` calls in manifest order and submitted successfully; filling entities before provenance is rejected with SK-002; a submit missing provenance, carrying a trivial intent, or carrying partial labels is rejected with DS-025, DS-026 and DS-024 respectively; a submit with any broken section returns errors scoped to that section; and an abandoned skeleton does not become a dataset.

### M6: the runtime read path

`run_start` pinning `{dataset_id, dataset_version, blueprint_version}` and emitting `blueprint_version_mismatch` when the agent declares a different version while still serving. `fetch_step` with the full step identity resolution from PRD 5.5 (node id, then unique tool name, then tool name disambiguated by position, then structured error naming candidates). In-order pool draw with `pool_exhausted` warning and last-entry repeat. Idempotency on `(run_id, step_key, iteration)`.

**Accept when:** fetching the same step key twice returns byte-identical fixtures and advances nothing; a repeated tool name resolves correctly by position and errors with named candidates when it cannot; a loop past pool length repeats the last entry and sets the warning; a version mismatch warns and still serves; and no test can find a write path from `fetch_step` to a dataset.

### M7: Postgres, Mongo, containers, promotion

The Postgres and Mongo adapters against the same Protocol and the same integration test suite, parameterised over all three backends. Dockerfile. `docker-compose.yml` with `local` (service plus Mongo) and `shared` (service plus Postgres) profiles. `dataset_export` producing a portable bundle and `dataset_import` re-running full validation on arrival. Seeded deterministic `dataset_expand`.

**Accept when:** the full integration suite passes identically against SQLite, Postgres and Mongo; `docker compose --profile local up` gives a working service with Mongo in one command; a dataset exported from a SQLite store imports into a Postgres store and validates; and `dataset_expand` with the same seed produces byte-identical output across two processes.

### M8: the Python client

`agent-props-client`, separately installable. Generates the run id at construction. `fetch_step` and `record_step` carrying it. The three comparison helpers (`exact`, `schema`, `subset`) as pure functions with no network calls. Sync and async APIs.

**Accept when:** a test agent runs the worked example end to end against a live server, the comparison helpers are unit-tested against a table of cases including the tricky ones (subset with nested objects, schema with additionalProperties), and importing the compare module pulls in no network dependency.

### M9: the web app

Browse agents, blueprints and datasets. **The dataset list is a review surface, not a picker:** each row shows title, author, complete label set and the intent, because a stranger has to judge relevance without opening anything. Filter by label, by author handle, and by free text over title and intent. A dataset detail view shows narrative and intent side by side, since they answer different questions. Edit blueprint and dataset JSON in `vanilla-jsoneditor` with the emitted JSON Schemas wired in for live validation. Read-only React Flow view of a blueprint's node graph.

**Accept when:** a deliberately broken edit shows inline errors before save, a reviewer can find the Priya dataset by searching "repeat operator" and by filtering `author=pnair`, the list shows enough to judge relevance without a detail fetch, the graph view renders the worked example's full topology including the loop edge, and no mutation happens outside the tool surface.

### M10: publish outward

OTel spans for a run and its steps. Langfuse dataset-run linkage. `run_evidence` returning the bundle: expectation, actual, per-node expected versus actual, traversed path against `expected_path`, declared comparison mode, warnings.

**Accept when:** a completed run appears as a trace in a local OTel collector with one span per step, and `run_evidence` output is sufficient for the client's comparison helpers to grade the run with no further server calls.

### M11: TypeScript client — **DESCOPED by the owner, 2026-09-09. Do not build.**

See `docs/spec-rulings.md` R-68. Phase 1 now ends at M10. Nothing in the project referenced
this milestone when it was dropped and `client/typescript/` was never created, so there is no
residue to unwind. The original text follows for the record.

> Parity with the Python client. Deliberately last, so the contract is settled by real Python usage first.
>
> **Accept when:** the same worked-example end-to-end test passes from TypeScript, and run ids generated by either client are accepted by the other's server session.

## 5. CLAUDE.md content

Write this into the repo at M0.

```markdown
# agent-props

A blueprint-driven narrative fixture service for agentic systems. See `docs/prd.md` in the
project for product rationale before changing behaviour.

## Invariants (do not violate)
- The runtime is read-only. No code path writes to a dataset from a running agent.
- The service never grades and never gates. It returns warnings, never failures, for policy issues.
- No LLM client, no model API key, no judge anywhere in `src/`.
- Datasets are immutable and versioned. Edits are copy-on-write.
- Archive, never delete.
- No dataset without provenance: title, intent, complete labels, named author. No defaults,
  no "fill it in later". `author` is attribution, never authentication: do not build
  ownership or permissions on it.
- All randomness inside the service flows through the seeded source in `expansion/seeded.py`.
  No bare `random`, `uuid4` or `datetime.now()` in generation or expansion paths.

## Layering
`server/` -> `service/` -> `storage/`, `validation/`, `models/`.
`models/` and `validation/` import nothing from the others. No business logic in `server/`.
Tool functions parse, delegate, and shape the response. Keep them under 20 lines.

## Commands
- `uv run pytest` all tests
- `uv run pytest -m integration --store postgres` integration against one backend
- `uv run ruff check` and `uv run mypy src` must both pass before any commit
- `docker compose --profile local up` service plus Mongo, for authoring

## Testing
- Validation rules are the product. Every rule id in `contracts.md` needs a registry entry
  and at least one fixture in `tests/fixtures/broken/`. A test enforces this.
- Integration tests are parameterised over sqlite, postgres and mongo. A feature is not
  done until it passes on all three.
- Use the in-memory MCP `Client` against the server object for tool tests. Do not spawn
  subprocesses in unit tests.

## Style
- Python 3.12+, Pydantic v2, `mypy --strict`.
- Structured errors, never exceptions, for anything a user could cause.
- Every user-facing error carries a rule id and a JSON pointer.
```

## 7. Testing strategy

Four layers, in order of how much they matter here.

1. **Validation rule tests.** The largest suite. Table-driven from the broken-fixture corpus. Every rule id, both directions.
2. **Storage conformance tests.** One suite, parameterised over three backends. Written once against the Protocol, never per-adapter.
3. **Tool contract tests.** In-memory MCP client. Assert shapes and error envelopes, not prose.
4. **End-to-end.** The worked example, authored from skeleton to submitted dataset, then consumed by a test agent through the Python client, in every backend.

Property-based testing with `hypothesis` is worth it in exactly one place: the seeded expansion, asserting that the same seed always produces the same output and different seeds usually do not.

**Do not write tests that assert on human-readable error messages.** Assert on rule ids. Messages will be reworded.

## 9. What is explicitly not in scope

Repeating the PRD's non-goals here because they are the ones most likely to creep in during a build: no auth, no multi-tenancy, no CLI, no grading, no CI gating, no LLM, no dashboards, no tool-call interception, no hard delete, no writes from a running agent, no real or anonymised production data.

If a milestone seems to need one of these, it does not. Note it in `DECISIONS.md` and move on.
